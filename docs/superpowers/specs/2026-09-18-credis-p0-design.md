# Credis P0 论坛激励系统设计

日期：2026-09-18

状态：已确认设计

## 1. 背景与目标

本项目依据 `01-战略方案/激励计划/论坛能力盘点与开发PRD.md` 开发完整 P0 能力。业务系统以 [`linux-do/credit`](https://github.com/linux-do/credit) 为上游整体 Fork，而不是重新实现一套 NestJS 服务。

Fork 后的产品名为 **Credis**，对外稳定域名为：

```text
https://credis.example.com
```

论坛域名示例为：

```text
https://forum.example.com
```

项目目标：

1. 优先保留和验证上游已有的 OAuth/OIDC、社区用户、信任等级、Gamification、支付基础设施、API/Worker/Scheduler、PostgreSQL、Redis、OpenTelemetry 与 Next.js 前端；
2. 将 Credis 强化为以不可变积分流水为唯一账务事实的 LDC 账本；
3. 以本地真实 Discourse 实例验证论坛集成，不以模拟 API 替代主要端到端测试；
4. 完成 P0 论坛事件、计分、冲正、Gamification 投影、通知、对账与基础效果监控；
5. 初期与 Discourse 同机隔离部署，从第一天保留迁移至独立环境的接口和运维路径；
6. 当前阶段不接触或迁移生产论坛数据，部署验收后再单独执行真实数据迁移。

## 2. 关键决策

### 2.1 技术基线

- 整体 Fork `linux-do/credit`；
- 后端沿用 Go、Gin、GORM；

- 数据库沿用 PostgreSQL；
- 缓存、会话和任务基础设施沿用 Redis；
- 异步任务沿用 Asynq；
- 沿用 API、Worker、Scheduler 三种运行角色；
- 沿用 Swagger/OpenAPI、OpenTelemetry、健康检查与 Docker 构建基础；
- 不采用此前讨论的 TypeScript + NestJS 重写方案。

## 3. 系统边界与拓扑

### 3.1 初期同机部署

```text
同一台服务器
│
├─ 统一反向代理 / TLS
│  ├─ forum.example.com  → Discourse
│  └─ credis.example.com → Credis Frontend/API
│
├─ /var/discourse
│  └─ Discourse 官方 Docker
│     ├─ Discourse App
│     ├─ Discourse PostgreSQL
│     ├─ Discourse Redis
│     └─ uploads / backups / shared volumes
│
└─ /opt/credis
   └─ 独立部署单元
      ├─ frontend
      ├─ api
      ├─ worker
      ├─ scheduler
      ├─ Credis PostgreSQL
      └─ Credis Redis
```

即使同机，两套系统也不得共享：

- PostgreSQL 实例、数据库用户或数据目录；
- Redis；
- Docker Compose 项目；
- Docker 网络和数据卷；
-配置与 Secret；
- 备份目录；
- 日志目录；
- 数据库迁移脚本。

### 3.2 稳定通信接口

从第一天起，两套系统通过可远程使用的 HTTP(S) 接口通信，不依赖容器 IP、共享目录或跨库 SQL：

```text
Discourse → Credis
POST https://credis.example.com/webhooks/discourse

Credis → Discourse
HTTPS REST API at https://forum.example.com
```

所有地址通过配置注入。不得将 `localhost`、固定容器 IP 或直接访问 Discourse 数据库写入业务逻辑。

- Swagger、OpenTelemetry 和探针；
- Next.js 前端和管理页面。

这些能力先原样运行并建立基线，不重复开发。


- 勋章授予与撤销。

只有能力矩阵确认缺口后，才允许创建最小 Discourse 插件。不得修改 Discourse Core，也不得替换上游已经可用的集成。

### 4.3 非 P0 上游模块

支付、转账、商户、红包和争议模块：

- 保留源码；
- 默认通过 Feature Flag 关闭；
- 同时关闭前端入口、后端路由、Worker 和 Scheduler；
- 未完成安全和账务一致性验收前不得在生产启用；
- 相关余额写入口仍须最终统一经过新账本，以免未来启用时绕过流水事实。

## 5. 严格账本模型

### 5.1 上游现状与增强原因

上游当前主要通过 `User.available_balance`、`User.pending_balance` 等聚合字段，以及 `Order` 状态和原子 SQL 增减维护余额。其支付路径具有事务与并发保护，但未发现完整的独立、不可变逐笔账本，也不能仅从流水重建余额。

Credis 必须增强为：

```text
ledger_entries   = 唯一账务事实
ledger_accounts  = 可重建余额投影
orders           = 支付/订单业务事实
forum_events     = 论坛奖励来源事实
```

### 5.2 核心数据对象

新增或明确以下模型：

```text
forum_instances
forum_users
forum_events
contributions
rule_versions
rule_definitions
ledger_accounts
ledger_entries
settlement_batches
outbox_events
external_sync_records
reconciliation_runs
audit_logs
```

`forum_users` 与论坛用户的稳定关联键为：

```text
forum_instance_id + discourse_user_id
```

用户名、邮箱和头像仅为快照，不得作为账户唯一键。

### 5.3 账本流水

所有余额变化必须形成不可变流水，至少支持：

```text
earn
freeze
consume
release
pending_settle
refund
reversal
restore
opening
manual_adjustment
```

每条流水必须保留：

- 账户；
- 金额和余额桶；
- 各余额桶的有符号变动量；
- 来源论坛事件或业务对象；
- 规则版本；
- 结算批次；
- 幂等键；
- 原流水关联（冲正、退款或恢复）；
- 发生时间和入账时间；
- 审计信息。

第一版使用整数最小单位，禁止浮点数。每笔流水必须明确记录 `available_delta`、`frozen_delta` 和 `pending_delta`，未参与本动作的余额桶记录为零。

动作与余额桶变动约定如下，所有变动均以“增加为正、减少为负”表示：

| 动作 | available_delta | frozen_delta | pending_delta | 说明 |
|---|---:|---:|---:|---|
| `earn` | `+A` 或 `0` | `0` | `0` 或 `+P` | 即时奖励严格写 `(A,0,0)`；待结算奖励严格写 `(0,0,P)`，同一流水不得同时增加可用和待结算 |
| `pending_settle` | `+P` | `0` | `-P` | 待结算奖励到期后转入可用，不改变总额，并关联原 `earn` |
| `freeze` | `-A` | `+A` | `0` | 可用积分转入冻结，不改变总额 |
| `consume` | `-A` 或 `0` | `0` 或 `-A` | `0` | 直接消费可用写 `(-A,0,0)`；已冻结订单完成消费写 `(0,-A,0)`，不得先释放回可用再消费造成多余中间余额 |
| `release` | `+A` | `-A` | `0` | 取消订单或冻结失败时释放 |
| `refund` | `+A` 或 `0` | `0` | `0` | 已消费积分退回可用；退款本身关联原消费流水 |
| `reversal` | 按业务链当前桶位核定 | 按业务链当前桶位核定 | 按业务链当前桶位核定 | 待结算奖励撤销写 `(0,0,-P)`；已结算奖励须冲正结算后的可用积分，写 `(-P,0,0)`，不能机械反转原 `earn` 产生负 pending；若奖励已消费，允许可用余额因此为负，不得篡改消费历史 |
| `restore` | `+A` 或按核定桶位 | `0` 或核定变动 | `0` 或核定变动 | 对已冲正业务重新生效，必须关联原业务链 |
| `opening` | `+A` 或核定值 | `+F` 或核定值 | `+P` 或核定值 | 迁移期初余额，必须有审计证据 |
| `manual_adjustment` | 按批准值 | 按批准值 | 按批准值 | 需要双人/管理员审批和审计 |

账户投影不变量为：`available_balance = Σ available_delta`、`frozen_balance = Σ frozen_delta`、`pending_balance = Σ pending_delta`。总账余额为三桶之和；`freeze`/`release`/`pending_settle` 的三桶总和保持不变，`consume` 减少总账余额，`refund` 增加对应退回金额。撤销沿来源业务链查找奖励当前所在桶位：未结算部分冲减 pending，已结算部分冲减 available；不能仅对最早的 `earn` 逐桶取反。若奖励已消费，可用余额允许低于零，但不得改写或删除历史消费。任何动作都必须满足动作定义、来源和审批约束。

结算链必须可追溯：`pending_settle` 关联原待结算 `earn`，`reversal` 关联被撤销奖励及其结算链；同一待结算金额不得重复结算，结算和撤销的累计金额均不得超过原奖励金额。验收至少覆盖“待结算前撤销”“部分结算后撤销”“全部结算后且已消费再撤销”。

### 5.4 渐进式改造上游余额模型

第一阶段采用事务内双写：

```text
1. 写 ledger_entries
2. 更新 ledger_accounts 投影
3. 更新兼容所需的原 User 余额字段
4. 写 outbox_events
5. 提交事务
```

持续验证：

```text
原 User 余额
= ledger_accounts 投影
= ledger_entries 净额
```

待所有旧余额写入口收口后，Ledger Service 成为唯一写入口。原余额字段可继续作为兼容投影，但管理接口不得直接修改余额。

### 5.5 事务边界

单个记账事件在同一个 PostgreSQL 事务中完成。额度校验不得发生在并发互斥之前：

```text
BEGIN
  锁定并确认原始事件未处理
  按 occurred_at 读取生效规则版本
  按稳定顺序锁定或创建用户日额度行、对象额度行和账户行
  在锁内校验资格并以条件原子更新占用日额度/对象额度
  写入不可变 ledger_entry
  更新账户投影与必要兼容投影
  写入 outbox_event
  写入处理结论
COMMIT
```

额度使用独立投影（如 `quota_usages`），不同额度采用不同的稳定作用域，规则版本只记录计算依据，不默认构成重置边界：

| 额度类型 | 稳定唯一键 | 重置/承接语义 |
|---|---|---|
| 用户每日基础分 | `quota_policy_id + account_id + business_date(Asia/Shanghai)` | 仅按北京时间自然日重置；同一天发布新规则版本继续承接当日已用额度 |
| 内容累计点赞分 | `quota_policy_id + target_post_id + like_scope` | 跨日期、跨规则版本累计，帖子生命周期内不自动重置 |
| 内容累计收藏分 | `quota_policy_id + target_post_id + bookmark_scope` | 跨日期、跨规则版本累计，帖子生命周期内不自动重置 |
| 其他对象额度 | `quota_policy_id + stable_target_type + stable_target_id` | 按明确业务生命周期累计，除非经过受审计的数据迁移，不因发布规则而清零 |

`quota_policy_id` 是跨规则版本稳定的策略身份；`rule_version_id` 保存在额度明细和流水中用于解释当时采用的上限与奖励金额。新版本提高上限时，新增差额空间可供后续事件使用；降低上限时不冲正既有合法奖励，但在累计已用量低于新上限前不再发放。若产品确需重置额度，必须创建新的 `quota_policy_id`，形成迁移决议、明确生效时间并完成历史影响评审，不能把普通规则发布隐式当作重置。

首次使用通过唯一约束安全 upsert；涉及多个额度时按额度类型和稳定键排序加锁，避免死锁。在锁内计算：

```text
remaining = max(cap_at_event - used, 0)
actual_award = min(expected_award, remaining)
```

随后以条件更新占用 `actual_award`，并在流水/计分结果中同时保存 `expected_award`、`actual_award`、`capped_amount` 和 `cap_reason`。`actual_award = 0` 时保存明确的封顶结论但不创建零金额账本流水。额度占用、额度释放、流水和账户投影必须同事务提交；取消、冲正或迟到事件是否释放额度由额度策略声明，释放后不得低于零。

外部 HTTP 调用不在该事务内执行。并发验收必须覆盖：

- 用户日额度或对象额度仅剩 1 分时，两个不同且合法的事件同时处理，最终合计最多入账 1 分；
- 普通主题应得 5 分、用户日额度仅剩 1 分时，`expected_award=5`、`actual_award=1`、`capped_amount=4`；
- 同一帖子跨天或发布新规则版本后，点赞 100/收藏 250 的已用额度不重置；
- 同一天发布新规则版本后，用户日额度继续承接当日已用量；
- 所有场景中额度投影、流水和余额保持一致。

### 5.6 幂等

建立三层幂等：

1. **接收幂等**：优先使用论坛提供的不可变 `source_event_id`，唯一键为 `forum_instance_id + source_event_id`；不存在可靠源事件 ID 时，按事件类型生成包含行为主体、对象、动作和来源版本的规范键：`forum_instance_id + event_type + actor_user_id + target_type + target_id + action + source_version`。点赞和收藏必须包含行为用户，回复、解决方案、标签和举报必须包含其稳定业务主体/对象 ID，不能仅以帖子 ID 去重；
2. **记账幂等**：业务动作、账户、来源事件、规则版本组成唯一键；
3. **外部同步幂等**：目标系统、目标对象、操作和账本版本组成唯一键。

当源事件 ID 和可靠来源版本均缺失时，系统保存完整原始 Payload、接收时间和候选规范键，将事件置为 `pending_review`，不自动计分。核查后由受审计的决议绑定稳定事件键；重放必须复用该键。禁止仅按接收时间或 Payload 哈希直接认定两个业务事件相同，因为同一用户可能合法重复执行“新增—取消—再次新增”。

重复合法事件返回成功但不重复记账。无法确认语义的事件进入 `pending_review`，不得默认发分。

### 5.7 行为状态、版本推进与乱序收敛

幂等只解决“同一事件不重复处理”，业务最终状态由版本化行为关系决定。每种可撤销行为必须定义稳定关系键，例如：

```text
点赞/收藏：forum_instance_id + actor_user_id + target_post_id + reaction_or_bookmark_kind
Solved：   forum_instance_id + topic_id + accepted_post_id
标签：     forum_instance_id + topic_id + tag_id
举报：     forum_instance_id + reviewable_id + decision_kind
```

`behavior_relations` 保存关系键、源版本/源更新时间、当前状态（`active`/`inactive`/`unknown`）、最后已应用事件和状态历史。处理规则：

1. 有可靠单调版本时，仅更高版本推进当前状态；低版本迟到事件保留审计，不能直接覆盖当前状态；但若它补全了此前缺失的合法激活历史，仍须按第 6–9 条重算额度与账务；
2. 无单调版本但有权威 API 当前状态时，事件先触发核查，以 API 状态和可审计时间线收敛；
3. 撤销先到而新增未到时，保存 `inactive` 关系和“前置事件缺失”状态，不创建负奖励；后续迟到新增只补齐历史，不直接改变当前状态或补发当前奖励，但须依据额度策略补建历史占位；
4. 新增→取消→恢复形成同一关系的版本链。每次状态转换按“前一已确认状态 → 新状态”计算差额，不按单个事件名称直接加减；
5. 同一事件集合不论到达顺序，重放后必须得到相同的关系状态、净流水和额度使用量；无法建立顺序的事件进入 `pending_review`；
6. **额度占位与奖励周期分开建模**：`quota_claim` 保存额度策略、关系键、首次合法激活事件、确定性排序键 `occurred_at + source_event_id/stable_event_key`、获配金额和相关奖励周期。`release_on_reversal=false` 时，同一 `quota_scope_key + behavior_relation_key` 在该额度作用域生命周期内只有一个稳定 claim（对象累计额度为该对象的策略生命周期，用户日额度为相应自然日）：取消后该 claim 保留原额度占位，恢复复用原获配金额（以新的 `restore` 流水恢复净奖励），不得生成第二个额度请求；重复恢复不再增加占位。新规则改变金额时，原 claim 的获配金额不隐式重置，差额需通过独立规则迁移决议处理；
7. `release_on_reversal=true` 时，取消使当前奖励周期的 claim 退出有效额度集合；恢复是新的激活周期和新的 claim，按该周期首次激活时间参与分配，可能因其他有效关系先占满额度而不获奖励。两种策略均以当前有效关系和获配金额计算净应得，不把已撤销的旧奖励保留在余额中；
8. 撤销先到、后收到更早的新增时，若策略不释放额度，必须补建该关系首次激活的历史 claim；若释放额度且当前关系无效，则仅保留历史周期，不占当前额度。迟到事件改变 claim 集合或排序时，在关系锁和额度锁内对受影响作用域确定性重算，以补发/冲正流水调整此前分配，保留原流水；
9. 对象上限、用户日上限及释放策略均使用上述 claim 分配结果更新 `quota_usages`。没有可靠发生时间或稳定排序键时不得自动重排，进入 `pending_review`。

验收必须以同一组新增、取消、恢复事件的多种排列重放，验证最终行为状态、流水净额、余额桶和日/对象额度完全一致；至少覆盖：新增→取消、取消→新增（低版本新增只补历史与必要占位、不直接发分）、新增→取消→恢复，以及上述每种排列中再插入一个竞争同一对象上限的有效点赞/收藏事件。尤其要验证上限已被 100 个有效点赞占满，其中一个取消再恢复：`release_on_reversal=false` 时该关系复用原 claim、占位仍为 100、净奖励恢复为 100 分；`true` 时恢复作为新周期参与额度竞争，两种策略均不得重复占位或超发。

### 5.8 冲正

原流水不可修改或删除。撤销通过反向流水处理：

```text
原流水：bookmark.reward   +5
冲正：  bookmark.reversed -5
关联：  reversal_of = 原流水 ID
```

同一原流水最多存在一个有效全额冲正。后续恢复形成新的恢复流水并保留完整链路。

## 6. Transactional Outbox 与异步任务

账本事务只向 PostgreSQL 写 Outbox：

```text
账本提交
→ outbox pending
→ Worker 调用 Gamification / 通知 / 对账目标
→ 明确成功：记录远端业务标识并标记 completed
→ 明确失败：记录原因并按策略重试
→ 结果未知：保持阻塞，按目标交付契约核验请求终态；只查到当前值不能证明旧请求结束
```

每种外部操作必须在适配器中声明交付契约：

- **支持远端幂等键**：发送稳定的 `external_operation_id`，重试复用同一键；
- **支持按业务标识查询**：请求前后记录远端对象 ID/自定义字段；结果未知时必须查询对应操作的执行终态。仅能读取目标当前值不属于可核验的操作终态，不得据此解除后续版本阻塞；
- **不支持幂等或查询**：明确为至少一次交付，进入 `delivery_unknown` 人工核查队列；对私信、邮件、原帖回复等用户可见通道，正文或元数据携带不可见/低干扰业务标识（目标能力允许时），确认未送达后才重发；
- **Gamification 投影**：优先使用“设置/更新至目标累计值”而不是“增量 +N”。每个论坛用户/排行榜目标维护单调 `projection_version`，同一目标的 Outbox 串行领取；发送前读取数据库最新目标值和版本，尚未发送的旧版本任务标记 `superseded`。绝对值写入仅使同一请求重试收敛，不能阻止较早的远端在途请求后来覆盖新值；
- **在途与结果未知**：`delivery_unknown` 及客户端超时均视为旧请求仍可能执行。查询远端当前**分值**只能用于对账，不能证明旧请求终止；解除阻塞必须具备可核验的远端操作终态、远端带版本的条件写入/栅栏，或已验证的远端最大执行/排队时限且经过该时限后再次核查。只有核实旧请求不可能再写，才能发送后续版本；
- **无终态保证的目标接口**：若只有分值查询、没有操作终态、条件更新或有界执行时限，保持该目标的后续写入阻塞并进入人工处置，不承诺“旧写不会覆盖新值”。若业务明确接受最终一致性，须单独批准降级契约：允许晚到旧写、按周期持续查询远端并重放数据库中的最新目标值，记录偏差、恢复时长和告警；这种模式不得作为严格实时同步验收通过；
- **仅支持增量的 API**：必须为每个操作使用远端可核验业务 ID；没有远端幂等或查询能力时，不能自动执行贡献榜增量重试，进入人工核查。

Gamification 验收必须注入：远端原本为 10，旧的“设置 10”仍在执行，查询仍返回 10；此时目标值变为 15，不得仅凭查询结果解除阻塞。还要模拟旧请求晚于新请求完成：具备远端终态/条件更新/已验证时限的模式必须阻止旧写覆盖，远端最终为 15；仅接受最终一致性的模式必须记录短暂回退并由持续对账修复至 15，不能宣称强一致。奖励冲正使目标值下降的场景也必须通过，不能简单取最大值。

Outbox 记录至少保存稳定操作 ID、目标、请求摘要、远端幂等能力、尝试次数、结果状态、远端业务 ID 和核查证据。Worker 在发送前领取带租约的任务；租约到期只表示可核查，不表示可直接重发。

Redis/Asynq 不作为唯一事实源。Redis 丢失后，系统必须根据 PostgreSQL 中的原始事件、Outbox、同步状态和调度游标恢复任务。验收必须注入“远端已成功，但客户端响应丢失”和“远端已成功，但 Worker 在本地标记完成前崩溃”，验证可幂等通道不重复，不可幂等通道进入结果未知核查而非自动重复发送。

队列优先级：

```text
critical    Webhook 后的账本处理、冲正
normal      Gamification、通知
maintenance 对账、指标快照、历史重建
```

资源紧张时可暂停 `maintenance`、降低 `normal` 并发，但不得丢弃已经接收的可信事件。

## 7. 规则引擎与 P0 范围

规则版本包含生效区间、时区、状态和发布审计。事件必须按 `occurred_at` 匹配规则，不能用当前规则重算旧事件。

P0 规则：

| 行为 | LDC | 关键约束 |
|---|---:|---|
| 普通主题首帖 | +5 | 与回复共享北京时间每日基础分上限 |
| 回复/评论 | +1 | 与普通主题共享每日基础分上限 |
| 合格 Demo 首帖 | +50 | 不叠加普通主题，不占基础分上限 |
| 内容收到有效点赞 | +1 | 每条内容最多 100，Reactions 口径版本化 |
| 内容收到有效收藏 | +5 | 每帖最多 250，事件能力验证通过后启用 |
| 明确解决方案 | +10 | 给答案作者，自答不发 |
| 合格 Demo 获精华 | +100 | 非 Demo 精华不发 |
| 有效举报 | +10 | 管理员确认成立，同一问题去重 |

点赞、收藏、Solved、精华、举报结论和内容有效性发生变化时按净应得计算差额；已入账部分形成冲正。

## 8. 同步、通知、对账和分析

### 8.1 Gamification

Gamification 仅作为累计有效贡献分的展示投影。正式启用 Credis 计分前，必须完成论坛侧配置和基线核对：

- 将 Discourse Gamification 内置主题、回复、点赞、阅读、访问、解决方案和邀请分值全部置零；
- 在正式计分切换前保存站点设置快照、既有排行榜快照、排除账号清单和切换时间；
- 将内置行为置零并完成基线核验列为 P0 上线门槛，不得仅以 Credis 外部分数同步通过代替；
- 明确 Credis 正式计分生效时间，生效前既有榜单不追补、不回算；
- 切换后只同步 Credis 产生的累计有效贡献收入及奖励冲正；
- 以测试用户逐项验证内置分值为零、Credis 投影可增加、奖励冲正可回退；
- 对账时区分切换前历史基线与切换后 Credis 投影，不把两者混为同一账本；
- 消费、冻结、释放和退款不降低贡献榜；
- 投影失败不回滚账本；
- 定期核对 Credis 累计有效贡献分与论坛投影。

上线验收必须同时提供站点配置证据、切换时间、既有榜单基线和切换后核对结果。

### 8.2 通知

通过 Outbox 异步执行：

- 处罚和积分状态：论坛私信与邮件；
- 内容缺项和迁移：原帖回复；
- 外部同步失败进入异常清单；
- 通知重试不得重复发送。

### 8.3 对账

定期通过 Discourse API 核查对象当前状态。空结果、权限不足、分页失败和数据源不可用不得解释为删除或撤销。

必须支持：

- 账户投影与流水净额核对；
- 冻结链核对；
- 已处理事件与账务/忽略结论核对；
- Outbox 长期未完成项核对；
- Gamification 投影核对；
- 规则版本时间覆盖核对。

### 8.4 P0 效果监控

效果监控不能从 LDC 流水反推全部贡献，必须独立保存用户批次、参与事件、贡献认定和状态历史，再与账本关联。

数据来源与最小历史：

| 数据对象 | 来源 | 必须保存 |
|---|---|---|
| 注册与用户批次 | Discourse 用户创建/API 对账 | 稳定用户 ID、注册时间/来源、注册周/月、事件时 TL/角色、首次参与/贡献/LDC 时间 |
| 参与事件 | 主题、回复、点赞、收藏、技术反馈和举报事件 | 稳定事件 ID、用户、对象、发生/采集时间、状态、撤销/恢复、完整性 |
| 合格 Demo | 板块、Form Template 字段、有效状态、精华标签 | 提交、确认有效、推荐、撤销时间及规则版本 |
| 有效解答 | Solved 关系与自答判定 | 接受、取消、答案作者、问题作者、有效状态历史 |
| 优质技术内容 | 受限精华标签，或当期点赞/收藏阈值 | 认定路径、阈值版本、达到/跌出阈值时间；排除已归类 Demo、解答和反馈的记录 |
| 技术/产品/Bug 反馈 | 结构化表单、状态标签、Assign/运营判定 | 提交、受理/核验、确认有效、采纳、解决/上线、撤销状态历史；从“确认有效”开始计入核心贡献 |
| 社区举报 | Reviewable/审核结论 | 提交和成立状态，可用于参与与治理分析，但明确排除核心有效贡献 |
| LDC 与使用 | 账本、订单与商城事件 | 来源贡献、应发/实发、入账/冲正、余额和使用结果，不包含履约敏感信息 |
| 背景与基线 | 升级、活动、发布、规则、故障记录 | 上线前冻结快照、背景事件区间、数据完整性和适用规则版本 |

`contributions` 必须保存稳定贡献 ID、排他 `core_type`、方向、当前状态、认定依据和规则版本；`contribution_state_history` 追加保存每次状态变化。四类核心贡献为合格 Demo、有效解答、优质技术内容、技术/产品/Bug 反馈，同一来源记录在同一统计窗口只归入一个核心类型；状态深化和互动不得重复增加贡献数。社区举报不进入核心贡献、30 天贡献激活或再次贡献。

上线前必须冻结可复算的基线快照，记录统计窗口、分子、分母、排除数、观察成熟度和数据完整性。建立注册、7 天参与、30 天有效贡献、LDC 入账和 30 天再次贡献链路；未满观察窗口、权限失败、分页不完整、待审核和任务失败不得显示为零或进入相应分母。

验收样例至少覆盖：

- 同一内容从技术反馈确认有效后计入，随后采纳/解决只深化状态、不重复计数；
- 一个来源同时满足 Demo、精华和点赞阈值时按排他规则仅归入一个核心类型；
- Solved 取消后从当前净有效解答移除，但保留历史状态；
- 社区举报成立可触发 LDC，但不进入核心贡献；
- 未完成 7/30 天观察窗口的注册批次显示“观察中”；
- 任一指标可下钻并用来源事件、贡献状态历史、账本流水和快照重算。

## 9. 错误状态与恢复

事件状态至少包括：

```text
received
validated
processing
processed
ignored
pending_review
failed_retryable
failed_terminal
reversed
```

处理规则：

- 无效签名直接拒绝，不作为可信事件；
- 合法但字段不足的事件保留原始记录并进入 `pending_review`；
- 规则不适用必须保存 `ignored` 原因；
- 暂时性错误进入重试；
- 达到重试上限后进入异常清单；
- 人工补发、重放、改判和冲正记录操作者、原因和关联链；
- 外部回写失败不撤销账本；
- 不提供直接改余额的生产接口。

## 10. 安全设计

- OAuth Secret、API Key、Webhook Secret、数据库凭证只通过 Secret 管理或受控环境文件注入；
- 日志不得记录令牌、签名密钥、券码、收件信息或敏感 Payload；
- Webhook 验证签名、来源实例、时间窗口和请求体大小；
- Discourse API 使用专用系统账号和最小权限 Key；
- 管理权限独立控制，不以论坛信任等级自动授予；
- 数据库和 Redis 不暴露公网；
- Feature Flag 同时约束页面、路由和后台任务；
- 依赖与镜像固定版本，CI 执行 Secret、漏洞、许可证和静态分析检查；
- 正式数据与测试数据隔离。

## 11. 测试策略

测试分五层：

1. 上游基线与回归测试；
2. 账本和规则单元测试；
3. PostgreSQL/Redis/Asynq 集成测试；
4. 本地真实 Discourse 端到端测试；
5. 部署、重启、备份恢复和同机拆分测试。

关键不变量：

```text
账户投影 = 不可变流水净额
处理过的可信事件 = 明确不计分结论或有效流水
外部同步失败 ≠ 账本失败
重复投递 ≠ 重复入账
Redis 丢失 ≠ 账务事实丢失
规则变化 ≠ 重算历史事件
```

真实 Discourse 场景至少覆盖用户、主题、回复、点赞/撤赞、收藏/取消、Solved 接受/取消、精华、举报、勋章、删除/恢复、重复、乱序和迟到事件。

## 12. CI/CD 与数据库变更

Credis 独立仓库至少执行：

- Go 格式、静态检查和单元测试；
- 前端格式、类型检查、测试和构建；
- PostgreSQL 集成测试；
- Redis/Asynq 测试；
- 数据库迁移测试；
- 账本不变量测试；
- Feature Flag 关闭测试；
- 镜像构建；
- 依赖、Secret、漏洞和许可证检查。

数据库变更要求：

- 使用显式版本化迁移，不只依赖运行时 `AutoMigrate`；
- 发布版本绑定应用版本、Schema 版本和上游 commit；
- 破坏性迁移采用“扩展 → 双写/回填 → 切换 → 清理”；
- 回填任务可暂停、续跑、核对并保持幂等；
- 不通过迁移改写历史账本金额；
- 不假设数据库迁移可自动降级。

生产镜像使用固定标签和摘要，不使用浮动 `latest`。

## 13. 后期迁移至独立环境

当论坛体验、CPU、内存、磁盘 I/O、Webhook 积压、日结时长、备份窗口或故障隔离需求表明同机部署不再合适时，将整套 Credis 迁移到独立环境。

迁移使用“单一接收入口 + 单一消费租约 + 最终增量同步”，不得在普通 DNS 传播期间让新旧 API 同时独立写账。步骤如下：

1. 在新环境部署与旧环境完全相同的应用和 Schema 版本，但保持 API 只读、Worker/Scheduler 停止；
2. 降低旧 Worker 并发并暂停 `maintenance` 与非关键外部同步，旧 API 继续作为唯一 Webhook 接收入口；
3. 对旧 Credis PostgreSQL 做一致性检查和基线备份，在新环境恢复；
4. 建立 PostgreSQL 流复制、受控增量同步或可核验的 WAL/增量导入，使新库追平旧库；Redis 队列不作为迁移数据；
5. 完成新环境只读核查、Discourse API 出站测试和内部健康检查；此时新 API 不得接收生产写入；
6. 进入短维护窗口：由稳定反向代理将 `credis.example.com` 的 Webhook 路径固定路由到旧 API，并对管理写接口停写；不得依赖 DNS TTL 直接切换接收入口；
7. 旧 API 完成已接收请求落库后进入只读，记录最后事件序号/时间和数据库 LSN；完成最终增量同步并核对旧新事件数、流水净额、账户投影、Outbox 和同步游标；
8. 使用数据库互斥租约/栅栏令牌保证旧新 Worker、Scheduler 不可同时取得消费权；撤销旧环境租约后，才允许新环境取得新一代栅栏令牌；
9. 在反向代理层原子切换 `credis.example.com` 到新 API，再启动新 Worker/Scheduler；旧 API 保持只读并拒绝写入，即使 DNS 或连接缓存仍指向旧主机也不会产生双写；
10. 执行真实测试事件，核对接收、记账、Outbox、Gamification 和通知，并持续监控遗漏、重复和队列积压；
11. 只有满足“新环境健康、最后事件游标连续、账本不变量成立、外部同步可重试”才宣告切换成功；
12. 若切换失败且新环境尚未产生业务写入，可将代理切回旧 API并重新授予旧消费者新一代租约；若新环境已产生写入，则禁止直接双向回切，必须先停写、以唯一主库为准完成反向增量同步和一致性核验；
13. 旧环境保留限时只读回滚窗口，验收后再下线容器与数据卷。

迁移前必须演练接收入口切换、最终增量同步、租约失效、切换失败和回退。该过程不得要求修改业务代码或 API 协议。

## 14. 真实论坛迁移边界

当前阶段不执行真实数据迁移。部署验收后单独实施：

1. 备份旧论坛数据库、上传文件、站点设置、插件、主题和环境配置；
2. 在新服务器恢复论坛备份；
3. 对账用户、主题、回复、标签、勋章、私信、上传和配置；
4. 重新验证 OAuth、API、Webhook、Gamification 和事件能力；
5. 核实恢复后 Discourse 用户 ID 是否保持；
6. 建立 `forum_instance_id + discourse_user_id` 映射；
7. 定义正式规则版本和计分生效时间；
8. 生效时间以前的历史行为不自动追补；
9. 静默试算并核对；
10. 通过验收后正式结算和切换流量。

如需导入期初积分，必须生成可审计的 `opening` 流水，不得直接修改余额。

## 15. 实施阶段

### 阶段 1：Fork 与上游基线

- 创建 Credis 独立 Fork；
- 固定上游 SHA 和许可证；
- 原样运行 Frontend、API、Worker、Scheduler、PostgreSQL、Redis；
- 建立基线测试；
- 默认关闭非 P0 模块；
- 作为 submodule 接入当前仓库。

### 阶段 2：现有论坛集成盘点

- 验证 OAuth/OIDC、用户字段、信任等级和 Gamification；
- 实测全部 P0 事件；
- 输出能力矩阵；
- 只针对已确认缺口设计最小插件。

### 阶段 3：不可变账本增强

- 新增事件、规则、流水、投影、冲正、批次、Outbox、同步和审计；
- 事务内双写并持续对账；
- 收口所有余额写入口。

### 阶段 4：P0 规则与论坛事件

- 实现全部 P0 规则、上限和版本化；
- 支持重复、乱序、迟到、撤销、恢复和改判；
- 必要时补充最小 Discourse 插件。

### 阶段 5：同步、通知和监控

- Gamification 投影；
- 私信、邮件和原帖回复；
- API 对账；
- 健康检查、指标、链路追踪和异常清单；
- P0 效果监控基础链路。

### 阶段 6：Discourse 升级验收、板块标签盘点与上线门槛

- 在后续预发布环境使用生产脱敏副本完成目标 Discourse 稳定/ESR 版本升级演练；
- 固定版本、清理并入 Core 的官方插件 clone 行，完成 PostgreSQL、插件、主题、站点设置和 upcoming changes 回归；
- 全量盘点论坛板块、子板块、标签和标签组，输出稳定 ID、权限、模板、通知、计分范围和目标映射；
- 先生成板块/标签迁移 dry-run 影响报告，记录旧新映射、主题数量、权限和积分映射影响；
- 升级验收和 dry-run 未通过前，不得进入正式 LDC 结算；
- 区分当前全新本地 Discourse 测试数据开发，与后续生产脱敏副本升级验收；
- 真实论坛数据迁移仍作为部署验收后的独立阶段，不在当前开发阶段执行。

### 阶段 7：部署与迁移准备

- 同机生产部署模板；
- 独立环境部署模板；
- 备份恢复和拆分迁移演练；
- 后续真实论坛迁移清单；
- 上线门槛证据包：Discourse 升级验收、板块/标签 dry-run、Gamification 置零与基线、P0 账本和端到端回归。
